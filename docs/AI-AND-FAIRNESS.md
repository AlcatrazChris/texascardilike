# 发牌随机性与混合 AI

## 当前发牌方式

`lib/cards.mjs` 创建 52 张不同的牌，使用服务端 `node:crypto.randomInt` 驱动 Fisher–Yates 洗牌：从下标 51 递减到 1，在 `[0, i]` 中均匀选出 j，交换第 i 张与第 j 张。若每一步整数均匀且独立，每种完整排列的概率都是 `1 / 52!`。Node 的 `randomInt` 明确规避了取模偏差：[Node 官方文档](https://nodejs.org/api/crypto.html#cryptorandomintmin-max-callback)。

生产洗牌不接受客户端种子，不使用时间戳或 `Math.random()`，也没有按玩家、牌型或胜负结果重新发牌的逻辑。`shuffle(cards, rng)` 的随机源注入仅用于开发测试；生产 `deck()` 始终使用默认密码学随机源。

模拟发牌就是先生成一副完整随机牌堆，然后依规则依次取出：从庄家左边开始轮流发两轮手牌；翻牌前烧一张并发三张公共牌；转牌、河牌各烧一张再发一张。所有牌都从同一副牌中移除，因此不会重复。剩余牌堆与对手隐藏手牌只保留在服务端状态的加密凭证中，不以明文发送给客户端。

运行 `node scripts/audit-random.mjs` 可抽样 20,000 次，检查牌是否重复、首张各牌频次、卡方描述值和口袋对子频率。一次实际运行中，首张频次范围为 341–434（期望约 384.6），口袋对子为 5.715%（理论约 5.882%），卡方约 51.876，自由度 51。每次运行的数值都会变化；这是开发检查，不是随机性认证。

密码学随机与客户端可验证公平是两回事。当前没有 commit–reveal、可验证洗牌或不可变审计日志，不能让玩家独立证明运营服务端没有改动牌堆。若要实现可验证公平，需要另行设计多方种子承诺、密钥管理、局后适时揭示和可重放验证，同时保护未公开底牌。

## 本地 AI 的改变

最早的实现主要依据最大底牌、是否口袋对子以及当前牌型类别做随机决策。现在轻松 / 标准 / 进阶难度分别默认进行 96 / 240 / 480 次未知牌抽样，并依据对手公开加注、全下和投入量近似加权其手牌范围，再补完公共牌和计算权益。

抽样只排除 AI 自己的底牌与已经公开的公共牌，不读取真实剩余牌堆、玩家底牌或其他 AI 的底牌。测试会故意篡改这些未知信息，检查同一随机源下本地决策不受影响。模拟所用的直接五至七张牌评估器与独立结算评估器进行交叉校验。

决策会考虑模拟权益、跟注所需底池赔率、投入占筹码的比例、位置、对手数量和有限的风格差异，按合法范围生成加注候选。只有短筹码或河牌极强牌才把全下加入候选，避免深筹码频繁无依据全下。

这是对公开行动推断范围的近似权益估计，不是对真实对手范围的精确预测，也不是 GTO / CFR 求解器。样本数量与启发式范围有局限，尚未用大规模固定牌局对战测量评级或长期胜率；不能仅凭引入模型就保证 AI 达到职业水平。强牌价值下注频率已经提高，但仍保留慢打与合法过牌，没有增加强牌禁止过牌的规则。

## DeepSeek 接口与等待控制

已提供可选服务端接口。没有 `DEEPSEEK_API_KEY` 时完全使用本地 AI。

默认使用 `deepseek-flash`，显式关闭 thinking 模式，只要求 JSON `{"choice": 0}`，选择服务端已经生成的合法候选动作。模型不负责洗牌、发牌或结算，也不能任意指定下注金额。参考：[思考模式开关](https://api-docs.deepseek.com/guides/thinking_mode/)、[JSON Output](https://api-docs.deepseek.com/guides/json_mode/)。JSON 模式仍可能返回空内容，因此代码会验证解析结果、索引及候选范围；异常直接回退。

| 控制 | 当前实现 |
| --- | --- |
| 请求筛选 | 默认 balanced：每手首次有可选动作的 AI 决策（包含翻牌前），后续复杂局面或翻牌前较大加注；complex 保留旧版仅翻牌后筛选；always 每次操作尝试；off 关闭。均受预算、缓存和限流约束 |
| 单次 API 请求 | 最多尝试一次模型选择，避免各 AI 串行请求造成等待叠加 |
| 每手牌 | 默认最多实际调用四次，DEEPSEEK_MAX_PER_HAND 可设 1–12；重放旧凭证本身仍不能作为可信限流手段 |
| 共享流量预算 | 默认每个固定分钟 30 次、同一应用密钥最多 3 个并发；Vercel 使用 Redis 原子脚本跨实例控制 |
| 缓存 | 相同模型、底牌、公共信息、合法候选的决策缓存 30 秒；缓存键不包含带抽样噪声的权益估计，也不混用不同隐藏底牌 |
| 模型截止时间 | 默认 1,800ms，可设为 100–2,500ms，覆盖完整响应体读取；超时取消请求并使用本地策略 |
| Redis 截止时间 | 每次操作最多 250ms；不可用时不发模型请求 |
| 失败恢复 | 429 按 Retry-After 的秒数熔断 10–300 秒，缺省 60 秒；5xx / 超时 / 空或非法输出短暂熔断；不在当前动作里重试 |
| UI 与动作 | 模型只参与决定动作，完成后仍使用既有逐动作播放流程，动作不会被跳过 |

DeepSeek 官方目前说明 API 有账户并发限制，超过限制会返回 429；忙时还可能保持连接等待，因此不能承诺服务商固定响应速度：[官方限流与保活文档](https://api-docs.deepseek.com/quick_start/rate_limit/)。本项目的 30 次 / 分钟与 3 并发是主动设置的应用预算，不是对服务商额度的描述。默认模型本身等待预算为 1.8 秒，但整个 HTTP 请求还包含 Redis 操作、本地计算、网络和可能的冷启动，并非端到端 1.8 秒 SLA。

Redis 的缓存、租约和固定分钟预算通过 [Upstash REST API](https://upstash.com/docs/redis/features/restapi) 实现，无第三方 SDK 依赖。生产环境不把内存计数当成分布式限流：Vercel 下没有 Redis 配置时，会完全回退到本地 AI。本地开发允许进程内的限流与缓存，仅供单进程验证。共享预算按应用使用的密钥区分，若同一 DeepSeek 账户有其他应用或多个密钥，应统一规划账户总预算。

## 启用方式与验证范围

在 Vercel 服务端环境变量中配置：

```text
DEEPSEEK_API_KEY=<自己的密钥>
DEEPSEEK_MODEL=deepseek-flash
DEEPSEEK_TIMEOUT_MS=1800
DEEPSEEK_RPM=30
DEEPSEEK_CONCURRENCY=3
UPSTASH_REDIS_REST_URL=<Redis HTTPS 地址>
UPSTASH_REDIS_REST_TOKEN=<Redis REST token>
```

密钥不要放在网页输入框、前端源码或聊天中。本地开发服务器自动读取 `.env.local` 和 `.env`；复制 `.env.local.example` 并填写真实 key 即可在本地按需启用，不要求本地额外配置 Redis。生产 Vercel 仍要求 Redis 进行分布式限流。变更后重新部署 / 重启服务。完整说明见 [多人联机与本地配置](MULTIPLAYER.md)。

侧栏「AI 运行状态」展示当前实例配置、调用策略、实际请求 / 成功 / 失败 / 缓存数量和最近跳过原因。GET `/api/ai-status` 不返回密钥、提示词或手牌；统计仅限当前服务实例，重启清零，Vercel 跨实例情况请查看 `[river.ai]` 函数日志。`node scripts/ai-status.mjs` 检查当前终端配置；`node scripts/verify-deepseek.mjs` 会通过真实开局流程尝试一次付费模型调用。

2026-10-26 本地真实 DeepSeek 翻牌前调用成功一次，单次观测约 1 秒，不代表延迟保证。模拟接口测试覆盖合法候选、预算、缓存、429 熔断、网络挂起超时、本地回退与 Redis 命令；Upstash 实网及跨实例负载尚未验证。`.env.local.example` 是模板，不自动加载；实际配置放在 `.env.local`，修改后重启本地服务或重新部署。

翻牌前现按底牌强度、位置、开池与再加注压力判断范围，避免把多人摊牌权益直接当作开池门槛。后位适当扩大范围，优先采用约 2.5BB 加 limper 调整的开池尺寸。翻牌后增加干燥牌面持续下注与听牌半诈唬，降低合理价值下注门槛，同时保留慢打和面对大注的弃牌。这些是启发式策略改进，尚无长期胜率评级。
